## 2. Portfolio Summary

### Short description (38 words)

A website for an interior architecture studio built around a browser-based 3D room planner. Visitors draw a room, place real cabinetry that snaps flush to the millimetre, change finishes, walk through the result, and request a quote.

### Full case-study description (218 words)

This project pairs a restrained marketing site with a genuinely functional 3D interior configurator, both delivered in one Next.js application.

The configurator, "TOD Studio", is the centrepiece. A visitor sets real room dimensions in millimetres, then places modules from a 47-item catalogue. Modules behave like real cabinetry: they rotate and pin flush when dragged near a wall, latch against compatible neighbours with their backs aligned, and refuse to overlap. Worktops are never stored as objects — they are recalculated every frame from whichever base units currently form a contiguous run, so moving one cabinet re-templates the counter across the whole row automatically.

Three view modes share one scene: a measured 2D plan, an orbiting 3D view, and a pointer-locked first-person walkthrough with real collision response against the furniture. Any of 29 finishes can be applied per object and the surface updates immediately. Projects save and restore across sessions, undo and redo cover every edit, and a completed design can be submitted as a quote request with an itemised bill of materials attached.

The engineering that makes this credible is mostly invisible: oriented bounding boxes with separating-axis collision tests, a single millimetre-to-metre conversion boundary, procedurally generated materials so the app ships no texture files at all, and an end-to-end browser test that drives the full 25-step journey in CI.

## 3. Feature Extraction

Ordered by how much they would matter to a prospective client.

### Interactive 3D interior planner (TOD Studio) **[Verified]**
A complete configurator at `/studio`. Users define a room, place modules, adjust them, and see the result in real time. This is the project's reason to exist and the strongest possible demonstration that the team builds applications, not brochures.

### Magnetic placement — wall and module snapping **[Verified]** (`src/lib/snapping.ts`, 379 lines)
Dragging a unit near a wall rotates it to face into the room and pins it flush; dragging it near a compatible neighbour latches it with backs aligned and the gap closed. Clicking a catalogue item auto-places it by extending an existing run first, then finding free wall, then open floor. **Why it matters:** it makes a non-expert feel competent — layouts come out looking professionally set out without the user understanding why.

### Derived worktops **[Verified]** (`src/lib/worktops.ts`)
Counters are computed from the current arrangement rather than stored. Move a base unit and the worktop re-flows across the whole run. **Why it matters:** the design can never drift out of sync with itself, which is the usual failure of cheaper planners.

### First-person walkthrough **[Verified]** (`WalkControls.tsx`, `resolveWalkCollision`)
Pointer-locked movement at eye height with collision response against placed furniture, plus on-screen touch controls. **Why it matters:** standing inside a space is the moment a client believes the design.

A dimensioned 2D plan (orthographic), a 3D orbit view, and the walkthrough — one scene, three cameras.

## 6. Complexity / Standout Engineering

### Oriented bounding boxes + separating-axis collision **[Verified — `src/lib/geometry.ts`, `collision.ts`]**
**Challenge:** furniture rotates to arbitrary angles, so axis-aligned boxes produce false overlaps and units that visually fit get rejected.
**Implementation:** every module's footprint is an oriented box; overlap uses the separating-axis theorem with a tolerance so snapped units that merely *touch* are not treated as colliding. Walkthrough collisions depenetrate along the axis of least penetration in each module's local frame, so walking into a cabinet slides along it rather than sticking.

### Two-stage magnetic snapping **[Verified — `src/lib/snapping.ts`]**
**Challenge:** "snapping" that only aligns to a grid feels crude; real cabinetry aligns to walls and to its neighbours' backs at matching heights.
**Implementation:** a pure `resolveSnap` function applies wall snapping (rotate to face the room, pin flush) then module snapping (latch beside a compatible neighbour at the same tier, backs aligned), with distinct ranges and a height tolerance. Auto-placement scans in priority order: extend an existing run, then free wall in 50 mm steps, then an open-floor spiral — validating every candidate against the real collision test.

### Derived geometry instead of stored state **[Verified — `src/lib/worktops.ts`]**
**Challenge:** a worktop that is a stored object desynchronises the moment a cabinet moves.
**Implementation:** worktop runs are recomputed by grouping carriers on heading, top height and back line, splitting into contiguous stretches, and emitting one slab each. Nothing to migrate, nothing to invalidate, and re-templating is automatic.

### A single unit-conversion boundary **[Verified — `src/lib/units.ts`, `src/types/index.ts`]**
**Challenge:** mixing millimetres (the domain) with metres (Three.js) is the classic source of silent 1000× bugs.
**Implementation:** the type module documents the contract explicitly — every persisted length is millimetres, every angle degrees — and conversion happens exactly once, at the render boundary. As the handoff notes put it: if you are converting in two places, one of them is a bug.

### Zero-asset procedural material system **[Verified — `proceduralTextures.ts`]**
**Challenge:** 29 finishes as image maps means megabytes of downloads and a texture pipeline.
**Implementation:** every finish is drawn to a canvas at runtime from a PRNG seeded on the material id, so it is deterministic across reloads. Textures are shared by `(materialId, quantised repeat)` rather than cloned per mesh. A full demo kitchen renders in roughly **305 draw calls, 9.8k triangles, 11 textures** — measured, and recorded so a regression is visible. *(Frame rate on real GPU hardware is unverified — all measurement was done under software rasterisation in a container. **[Needs Owner Confirmation]**)*

### On-demand shadow mapping **[Verified — `LightingRig.tsx`]**
A directional light's shadow does not change when the camera orbits, so `shadow.autoUpdate` is disabled and the map is re-rendered only when the design changes.

### Gesture-scoped undo with a module-level drag session **[Verified — `plannerStore.ts`, `editor/interaction.ts`]**
**Challenge:** routing 60fps pointer movement through React re-renders the whole scene; naive history makes every mouse-move an undo step.
**Implementation:** a live drag writes through a module-level session object outside React. History snapshots once per gesture at `beginDrag` and pops the entry at `endDrag` if nothing actually moved, so a click never costs an undo. The drag controller listens on the canvas element rather than per-mesh, so a fast drag that outruns the cursor keeps tracking.

### Storage behind a repository interface **[Verified — `persistence.ts`]**
The planner only talks to `ProjectRepository`. localStorage is one implementation; swapping in a server store requires implementing the interface and changing nothing else.

### End-to-end journey testing in CI **[Verified — `tests/core-journey.mjs`, `ci.yml`]**
A 25-step Playwright script with 24 assertions drives the real production bundle in CI, covering placement, snapping distances, worktop generation, camera movement in walkthrough, save/reload/restore, and quote submission. `HANDOFF.md` documents eight bugs that passed typechecking and code review and were only caught by driving a real browser.
